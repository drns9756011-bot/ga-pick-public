# Customer DB payments

## Production activation

This integration requires NICEPAY **Server approval + Basic authentication** keys.
Client-approval or Bearer-token keys are not compatible. Confirm the merchant account
supports this product and the partner domain before enabling live checkout.
Checkout requires the modern `R2_` (live) or `S2_` (sandbox) client key prefix;
client-approval `R1_`/`S1_` keys fail closed rather than potentially charging before server validation.

In Cloudflare Worker **ga-pick-public**, register secrets (never commit values):

- `NICEPAY_CLIENT_ID`
- `NICEPAY_SECRET_KEY`

Variables:

- `NICEPAY_MODE`: `sandbox` for test merchant keys; `live` for production keys.
- `NICEPAY_ENABLED`: initially `false`. Set `true` only when ready to accept payments.

The admin Worker does not need the keys to display payment history or allocate credits.
Both Workers use the existing shared D1 database. Tables are created idempotently.

Register the card payment/cancellation webhook in NICEPAY merchant settings:
`https://partner.ga-pick.com/api/lead-payments/webhook`

The per-order return URL is generated by the server with a random state value.
Do not substitute a static return URL or remove the state query parameter.

## Verification

Use sandbox merchant keys first when available. Never test by automatically charging
a production card. The operator must perform any real card transaction themselves.
Sandbox payments never grant access to real customers or live allocation credits.

Validate a successful payment, cancelled checkout, declined card, duplicate callback,
return after session expiry, and full refund webhook. Check desktop and mobile return
flows. Cancellation in NICEPAY must remove access to assignments funded by that order.
Partial refunds conservatively suspend the whole order pending manual reconciliation;
there is no automatic partial-credit allocation or refund tool in this implementation.

## Accounting and retention

- Server-owned price: KRW 8,000 per customer allocation, 1-100 units per order.
- One-time purchases only; no subscription or recurring billing.
- Access does not disclose unassigned customers. Existing manually assigned customers
  retain their assignment-scoped access until their existing expiry/revocation.
- An atomic D1 batch creates the assignment and consumes one purchased unit.
- Revoking/deleting/expiring a customer does not replenish purchased units.
- Customer records and notes still expire after 30 days; the separate credit-usage
  ledger retains only random assignment/order IDs and timestamp, not customer details.
- Webhook data never directly grants access: the server re-reads NICEPAY's transaction.
- Unknown approval outcomes remain `processing`; do not automatically retry a charge.
  The order screen and existing hourly scheduled job reconcile by transaction lookup.
- The hourly job reconciles at most 25 oldest unchecked orders per run; webhooks are the
  primary timely refund mechanism. Provider downtime can delay revocation reconciliation.
- Disabling new payments does not disable reconciliation of existing transactions.
